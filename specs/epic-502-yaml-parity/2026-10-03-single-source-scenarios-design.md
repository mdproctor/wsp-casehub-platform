# Single-Source YAML Scenarios for Tutorials and Showcase Gallery

**Issue:** casehub-pages#466
**Date:** 2026-10-03
**Status:** Draft

## Problem

The showcase gallery and tutorials both demonstrate orchestration constructs using overlapping YAML content maintained in two places:

1. **Showcase** (`examples/samples/Scenarios/`): 8 companion `.ts` scripts embed scenario YAML as inline JS string arrays (`[...].join('\n')`). Each script has ~200 lines of identical boilerplate (parseScenario, createScheduler, event listeners, UI update) — only the `EXAMPLES` data varies.

2. **Tutorials** (`tutorials/`): `tutorial.yaml` files contain inline steps that demonstrate the same constructs through guided prose + live interaction.

The remaining 7 showcase scripts (Form Automation, Scenario Controller, Script Library, Step Catalog, Table Population, Composable Workflow, Parameterized Script) have custom logic and are out of scope.

## Design

### Shared scenario directory

A new `scenarios/` directory at the repo root contains standalone `.scenario.yaml` files organised by category:

```
scenarios/
  flow-control/
    sequential.scenario.yaml
    concurrent.scenario.yaml
    delay.scenario.yaml
    loop.scenario.yaml
    when-guard.scenario.yaml
    delay-decorator.scenario.yaml
    loop-until.scenario.yaml
    retry.scenario.yaml
    timeout.scenario.yaml
  coordination/
    signal-await.scenario.yaml
    mutex.scenario.yaml
    barrier.scenario.yaml
    channel.scenario.yaml
    ...
  composition/
    data-trigger.scenario.yaml
    orchestration-block.scenario.yaml
    ...
  ...
```

### File format

Each `.scenario.yaml` uses the existing envelope format with the standard `meta:` block:

```yaml
scenario: sequential-demo
meta:
  title: Sequential
  description: Steps execute one after another in declaration order.
  tags:
    - steps
    - flow-control
steps:
  - click: { role: button, name: "A" }
  - click: { role: button, name: "B" }
  - click: { role: button, name: "C" }
  - click: { role: button, name: "D" }
```

This is identical to the existing `ScenarioEnvelope` format — `ScenarioEnvelopeParser` on the Java side and `parseScenario()` on the TS side already read this. No new parsing code needed.

The `meta.tags` array carries category information (e.g. `flow-control`, `coordination`). The directory structure mirrors categories but is not the source of truth — tags are.

### Manifest

A `scenarios/manifest.json` file indexes all scenarios for the showcase companion script:

```json
{
  "categories": [
    {
      "name": "Flow Control",
      "scenarios": [
        "flow-control/sequential.scenario.yaml",
        "flow-control/concurrent.scenario.yaml",
        ...
      ]
    },
    ...
  ]
}
```

This is generated by a simple script (`scripts/generate-scenario-manifest.js`) that scans `scenarios/` subdirectories, reads `meta.title` from each file, and outputs the manifest. Same pattern as the existing `scripts/generate-samples.js` for the gallery.

### Generic companion script

A single `examples/samples/Scenarios/scenario-showcase.ts` replaces the 8 standard companion scripts. It:

1. Reads a `data-manifest` attribute from the `.page.yaml` to find the manifest path (or a category filter)
2. Fetches the manifest, then fetches each `.scenario.yaml` file for the selected category
3. Parses `meta.title`, `meta.description`, and `meta.tags` from each file
4. Builds the `<select>` dropdown dynamically at runtime (replacing the hardcoded `<option>` list in `.page.yaml`)
5. Uses the existing `parseScenario()` + `createScheduler()` + event listener pattern

The `.page.yaml` files for the 8 standard showcases converge to a single template with a `data-manifest` or `data-category` attribute:

```yaml
# In the HTML component that references the companion script:
# <div id="scenario-root" data-category="flow-control"></div>
```

The 8 existing `.ts` files are deleted. The 7 custom scripts remain unchanged.

### Showcase .page.yaml changes

The 8 standard showcase `.page.yaml` files are similar but not identical — they share the same layout (buttons, event log, state/step/time/progress, picker, YAML viewer) but have different dropdown options. Since the generic companion builds the dropdown dynamically, the `.page.yaml` files can be simplified to remove the hardcoded `<option>` elements.

Each of the 8 `.page.yaml` files keeps its existing layout but:
- Removes the hardcoded `<select>` options (companion script builds them)
- Adds `data-category="<category>"` to the root element

### Tutorial integration

Existing tutorial inline steps stay unchanged. For tutorial sections that demonstrate orchestration constructs also shown in the showcase, a new `scenario-ref:` key references a shared scenario file:

```yaml
sections:
  - title: "Sequential Execution"
    content:
      type: template
      path: content/sequential.md
    scenario-ref: flow-control/sequential.scenario.yaml
    steps:
      # Tutorial-specific steps (e.g. spotlight, editor-highlight) still inline
      - spotlight:
          target: { role: region, name: "event-log" }
          content: "Watch the steps execute in order"
```

When `scenario-ref` is present, the tutorial host:
1. Fetches the referenced `.scenario.yaml` file
2. Displays the YAML source in a read-only code viewer within the section (before the prose content)
3. Adds a "Run" button that executes the scenario via the existing scheduler
4. Tutorial-specific inline `steps` still execute when the user advances through the section — they are independent of the referenced scenario's execution

This is additive — tutorials without `scenario-ref` work exactly as before.

### Implementation scope

**In scope:**
- Create `scenarios/` directory with `.scenario.yaml` files extracted from the 8 standard companion scripts
- Create `scripts/generate-scenario-manifest.js`
- Create `scenario-showcase.ts` generic companion
- Update 8 `.page.yaml` files (remove hardcoded options, add data-category)
- Delete 8 companion `.ts` files
- Add `scenario-ref` support to `parseScenario()` / tutorial host
- Update `samples.json` generation to reference the generic companion for the 8 entries

**Out of scope:**
- The 7 custom companion scripts (Form Automation, Scenario Controller, etc.)
- Restructuring existing tutorial inline steps
- Backend (Java) changes — the `ScenarioEnvelopeParser` already reads this format

### File count

Current:
- 8 companion `.ts` files × ~200-350 lines each = ~2000+ lines of mostly-duplicated code
- YAML content embedded as JS string arrays

After:
- 1 generic `scenario-showcase.ts` (~200 lines)
- N standalone `.scenario.yaml` files (one per example, ~10-30 lines each)
- 1 manifest generator script (~50 lines)
- 1 `manifest.json` (generated)

Net: ~1800 fewer lines of duplicated JS, scenario content in its native format.
